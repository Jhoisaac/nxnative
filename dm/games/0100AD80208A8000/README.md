Update v983040 (display version 1.81, `main` build `68e3a0ea176a79f403b859d4addad8c3`) with its seven DLC (Kaigaku and Zenitsu (Infinity Castle) added to 1.02's five), SDK 16.2.3; 1.02 (v131072, `main` `437c43801a1c9aee25bc83d4e8b18c64`) was the build first brought up, and its rows stay registered. 1.81 changes only `main` (`subsdk0` and `sdk` are the same builds); its text is 128.4 MB, beyond one patch area's reach (see Found on this game), and its cooked data gives 128,462 shaders (113,089 in 1.02), so the shader tables are 1.81's. CyberConnect2's game on Unreal Engine 5 (TOC version 5, no engine version string in `main`), with gRPC (`npln`) and CRI middleware (ADX2 sound, `.usm` movies). 60 fps on the Mac (30 on the Switch).

Status: brought up on the Mac: the title, the story mode's chapter map and its battles at 60 fps, with sound and controller rumble. The profile is the NSP script's provisional one with `fps_target 60` and a prewarm list (1,502 lines) recorded on the Mac. Not tried on the iPhone yet.

## Frame rate

- **Current:** 60 fps (30 on the Switch). `t.MaxFPS` is 0 in this game: the cap is Unreal's fixed frame rate, `bUseFixedFrameRate=True` and `FixedFrameRate=30` in `DefaultEngine.ini`, so the engine steps exactly 1/30 s a frame and waits out the rest ([Unreal's fixed frame rate](../../../docs/reference/frame-rate.md#unreals-fixed-frame-rate-uenginefixedframerate)). The host writes `UEngine::FixedFrameRate` 60 (`[main+0xcd23388]+0xaf8`: the `GEngine` pointer, and the property offset from Unreal's reflection data at `main+0x9d703d8`) and `rhi.SyncInterval` 1 (`main+0xcbfb958`), gated by this build; the game puts the fixed rate back at each load and the host writes it again.
- With a fixed frame rate the engine's delta time is 1/60 s, so the game's time-based logic keeps its speed (checked by hand in combat, no speed-up). Frame time p50 16.7 ms, p95 17.0–17.2 ms in battle on an M4 Pro; `DM_FPS_TARGET=0` keeps the game's 30.

## Memory

About 2.7 GB footprint at start and 4.8 GB in battle (headless, one-minute battle on Claro de la roca, the user's state with its 3.0 GB device archive and the app's 2.6 GB pipeline archive; Metal allocations 1.8 GB of it), current. Before the archive files were opened mapped it was 8.3 GB and 10.5 GB on the same route, and 8.4 GB rising to 12.2 GB in a player's 67-minute session ([Pipeline archive files read into memory](../../../docs/reference/memory.md#pipeline-archive-files-read-into-memory)).

## Rendering

- The particle sprites (Cascade) read their attributes from R32Float / RG16F / RGBA8 buffer textures at 4-byte offsets in Unreal's pools. Read in place on an M4 Pro, every attribute came one to three elements early: Waterfall Basin's blue water and the HUD seen through it came out red at water techniques and dashes (the scene colour, R11G11B10F, held reds of 10^3–3·10^4 over up to 15% of the screen, which the bloom spread as a red flash). Found with `DM_CTL texraw` of the scene colour and of the bloom chain (whose blur weights, `DM_NVN_CBDUMP`, were right), then Metal validation (`Offset of a buffer-backed texture … must be aligned to 16 bytes`). Such views are now read through an aligned copy ([Buffer textures at offsets below 16 bytes](../../../docs/reference/rendering.md#buffer-textures-at-offsets-below-16-bytes)).

## Files and shaders

## Found on this game

General changes first needed here; each applies to every game:

- **A system register read into x18** (`patch_nso.py` `emit_slot_copy`): one `mrs x18, tpidr_el0` among 3,812 `tpidr_el0` reads crashed the RHI thread ([System register reads into x18](../../../docs/reference/rewriter.md#system-register-reads-into-x18)).
- **Event descriptors** (`hle_net.c` `nn::socket::EventFd`, unit test `t_net`): gRPC's `poll` engine aborted at boot without them ([Event descriptors for gRPC's poll engine](../../../docs/reference/services.md#event-descriptors-for-grpcs-poll-engine)).
- **Pipeline archive compaction without lookup archives**: with the old files as the compiler's lookup archives, Metal's serializer crashed at the first start with 15 archive files and 421 bases taken from them; first fixed here by compiling the bases again, then upstream fixed it the same way, capturing them from the original shader functions, with a guard for a compaction that does not finish ([A compaction flush that crashes, then crashes every start](../../../docs/reference/shaders.md#a-compaction-flush-that-crashes-then-crashes-every-start)).
- The Mac audio device's 5 ms callbacks: CRI ADX2's 6-channel output keeps 3 × 240 frames in flight, so with the default 512-frame callbacks every 8th one found 496 frames queued and padded 16 (exactly 250 underruns and 83 ms in each 2000 callbacks: a click every 85 ms) ([The Mac's default I/O buffer](../../../docs/reference/audio.md#the-macs-default-io-buffer)).
- **Pipelines a scene draws the first time** (`nvn_mtl.m`): a draw served by a pulling stand-in is now recorded in `pso_user.tsv` at once; a prediction of every draw's stand-in and joining its build were measured and reverted (in play a joined draw waited longer than one compiling its own pipeline) ([Pipelines a scene draws the first time, on a cold archive](../../../docs/reference/shaders.md#pipelines-a-scene-draws-the-first-time-on-a-cold-archive)).
- **Shader map pairs** (`uepak.py` `ue5_shader_maps`, `shader_split.py` `ue_map_pairs`, current): the profile's `pso_pairs.tsv` (95,317 rows) comes from the shader maps of the 11 containers and the global cache, so the prebuild and vertex output padding use the real pairs; the key `ue_pair_skip_pipelines` names the velocity pipeline, open ([Unreal Engine 5 shader maps give the real vertex / pixel pairs](../../../docs/reference/shaders.md#unreal-engine-5-shader-maps-give-the-real-vertex--pixel-pairs)).
- **The depth mode for the bases made before the game runs** (`depth_mode zero` in `game.tsv`, current): the game sets near = 0, and the NSP script's prebuild and the app's offline archive were made for near = −w, so no draw found them and the host built every base again (the app log said `the game's depth mode is not the one built for`). With the key the app's archive is stamped `depth near=0`.
- **metal-tt's stack on a large archive** (`pso_offline.py` `big_stack`): with the pairs decoded from its Unreal shader maps (108,611 bases) the offline archive build overflowed `air-nt`'s 8 MB main thread stack after 36 minutes; `metal-tt` now runs with the hard limit, 64 MB ([metal-tt's backend overflows its stack on a large archive](../../../docs/reference/shaders.md#metal-tts-backend-overflows-its-stack-on-a-large-archive)).
- **Pipeline archive files mapped** (`nvn_mtl.m` `arch_open`, unit test `t_pso_archive`): Metal read every archive file into memory it kept, 5.8 GB of this game's footprint ([Pipeline archive files read into memory](../../../docs/reference/memory.md#pipeline-archive-files-read-into-memory)).
- **Graphics quality presets** (`ue_quality.tsv`, `dm/tools/ue_quality.py`, `hle_fs.c` `DM_UE_QUALITY`, current): replacement paks of the device-profile ini, chosen in the settings window ([Graphics quality](#graphics-quality)).
- **Another platform's textures** (`ue_pc_assets.tsv`, `dm/tools/ue_pc_assets.py`, `uepak.write_toc`, current, pilot): an IoStore patch container with the PC build's chunks of chosen packages, mounted with the Maximum preset's pak ([PC textures](../../../docs/agents/07-quality.md#pc-textures)).
- **A second patch area for a text beyond 128 MB** (`patch_nso.py` `SPLIT_MODE`, `loader.c`, current): update 1.81's `main` has 128.4 MB of text, out of reach of any one area before the base ([A second patch area after the key page](../../../docs/reference/rewriter.md#a-second-patch-area-after-the-key-page-for-a-text-beyond-128-mb)).

## Open

- Improvement (open, general): the `[RED]` line `vertex attribute format 0x27 (8 / 16-bit integer) feeds a float input` marks the CPU path of `vconv_bind` (`nvn_mtl.m`): an integer vertex attribute read by a float shader input is bound as the 32-bit register values Maxwell's fetch makes, converted on the CPU at replay into a staging buffer. The picture is right and the cost is small here (the `vertex conversion` line reports 0 vertices per submission most of the time), but a conversion on the GPU (a compute pass or vertex pulling) would remove the CPU work for every game that hits it.
- The red flash was fixed on this branch by an aligned copy made on the GPU before each draw (`tbal`, which split about a dozen render passes a frame in battle); it now relies on main's `tbuf_shadow` (a CPU copy per submission). Check Waterfall Basin's water techniques and dashes again on an M4 Pro.
- First pass of a scene on a cold archive: the draws' shader pairs are known only once drawn (the game ships no Unreal pipeline cache; `shader_pairs.tsv` holds only cover pairs), so the chapter start still waits about 0.8 s in all, spread over frames 6400–8100, once per scene and device (`pso_user.tsv` records them: the next start has no wait there). The shader maps in the cooked packages give the real pairs (resolved: `pso_pairs.tsv`, [Unreal Engine 5 shader maps give the real vertex / pixel pairs](../../../docs/reference/shaders.md#unreal-engine-5-shader-maps-give-the-real-vertex--pixel-pairs): 95,317 pairs, 2,009 of the 2,061 the game recorded; every VS × PS per map would be 2.26 million). Open: the 4 recorded pairs between global shaders and the 48 vertex-only draws are not in it, and the velocity pass's 19,085 pairs are left out by `ue_pair_skip_pipelines` because the game never draws it (cause not derived: the cooked config has FXAA and no motion blur, which agrees but is no proof). The 235–250 ms frames at the chapter load are on the game's loading screen (it sets the present interval to 0 around them): submit and present take 4 ms of them and texture uploads under 2 ms; the rest is the game's own loading or host calls on its threads that the longframe line does not time (open).
- The residency set adds and removes about 100 buffer texture views a frame in battle; the GPU stays near 10–13 ms of the 16.7 ms on an M4 Pro, but it is worth trimming before an iPhone build.
- A crash in the story fight Zenitsu vs Daki (2026-10-31, a player's window session, the 3rd–4th retry, mid-fight, about 38 minutes in): `CRASH sig=11 addr=0x24 pc=main+0x1cfb220` on the `RHIThread`. The game's NVN RHI sets a shader's parameters (`main+0x1cfb000`) for a recorded command whose shader is null (`ldrsb x24,[x19,#0x24]`, the shader's frequency). The recording side (`main+0x1d8874c`) stores a null shader with no check in two cases: the material's shader map has no shader of that type (`main+0x1d88afc`), or the lazy RHI shader creation failed on its own ensure (`main+0x1e58210`). Neither path takes a value from the host (the NVN shader creators always return an object), so the cause is open and so far looks like game-side; it does not involve the pipeline archive mapping. It came back twice more (Uzui vs Gyutaro on a retry, then a fight on its first attempt, a few minutes in), always with only uniform-buffer bindings (resource entry index 2, type 4) and no loose parameters. With `DM_PROBE=main:1d88afc,main:1d890cc,main:1edf568,main:1f58920,main:1e57f64,main:c2a9d0` (the four null arms of the recorder `main+0x1dc0800`, the shader-platform mismatch in `CreateRHIShader` and the engine's failed-check reporter; silent in normal play) none fired, so the command came from one of the about 130 inline recorders of the same command (vtable `main+0x9bd1c70`) with a shader type missing from its shader map. A fourth crash (about two hours in, frame 434,700, the game left paused for a while before the fight went on) was dumped with `DM_CRASH_PEEK=*main+cbfb4a0:12,**sp+60:4>8x64,sp:32` (the command being executed: the RHI loop stores it at `main+0xcbfb4a0`; the list from its head: the loop's list object is saved at `sp+0x60` by the faulting function's prologue, its first word is the first command and each command's next is at `+8`). The list is a mesh-draw list in the order the engine submits a mesh draw command: set graphics pipeline state with its initializer inline (vtable `main+0x9bcf7f8`, executed by `main+0x1d6ebd8`; the vertex shader at `+0x18`), set stream source (`main+0x9bd0560`), set shader parameters for the vertex then the pixel stage (`main+0x9bd1c70`), draw indexed primitive (`main+0x9bd0758`, `main+0x1dc02cc`). The failing command is the set-shader-parameters command just before a draw indexed primitive, so a pixel stage, with one uniform buffer bound. The list ran past the 64 blocks printed, 45 commands short of it, so its pipeline-state command was not seen. The game's lazy shader creation (`main+0x1e57db0`) returns null only when `CreateRHIShader` (`main+0x1e57ea0`) does, and that reports through `main+0xc2a9d0`, which the probes showed silent. Next: `DM_CRASH_PEEK=*main+cbfb4a0:16,**sp+60:10>8x4096,sp:32` (blocks up to 4,096, ten words each): the pipeline-state command before the failing one shows whether its pixel shader is null too (a draw without a pixel shader given pixel parameters) or set (the parameters recorded with another shader reference than the pipeline's). Three later sessions at the Maximum preset did not reproduce it: 2026-10-31 and 11-01 (about 1.2 h, the same fights replayed) and a story playthrough from the prologue to the same chapter plus versus fights (11-01, about 1.6 h, pool peak 5.5 GB of 8 GB, no abort, no [RED] line but the known vertex-format one).
